# 代码需求澄清

把一句「不对劲」变成一条记录和一段能粘回对话的话，同类差重复时立成规则，攒到一定量再按主题汇进档案。命令是 `qtfounder-lab code ...`（与正式版 `qtfounder` 区分），契约见 lab 仓 `src/cli/docs/api-references/`。

三件事：记一条（`code clarify`）、立一条规则（`code clarify --rule`）、把账本汇总成档案（写 profile 仓的 `code/intent/`）。前两件在协作现场做，第三件攒批做。

## 澄清的形状

澄清长得像一个改字请求，不是一个问卷。永远先把候选写出来让用户改，不空手问问题。

开口就三行加一句问：

```text
原以为：只改我指定的那一段
实际：整段重写
差：它不知道「指定」是排他的
要不要记？
```

用户要做的动作只有一个：回「对」，或改其中一行。不要求他重新陈述背景，不问「你具体想怎样」这类空问题——三行是从他的原话里摘的，摘不准是 agent 的错，他改一个字也算。

记完只回一行：`已记 req_xxx / clr_xxx，这次是第 N 次` + 那段可直接粘回的话。不复述流程、不解释设计。

## 记录规则

- 三级触发，由轻到重：A 过程中命中信号直接入账并一行回执（事后可改可删）→ B 收尾主动复盘（每次任务只提一次）→ C 用户召唤先定位对象再两问。
- 「差」的验收标准要宽：凡是「我以为的」和「实际的」对不上就算差——包括用户纠正我的设计判断（我定的默认值、我划的边界被推翻），不限于 AI 的行为失误。收得太窄，账本会只剩大事故，而那些「略微不对」的正是这工具存在的理由。
- 判定看「谁的判断被推翻」：被推翻的是 agent 的 → 记；被推翻的是用户自己的前一版定义（他改主意、重新定义）→ 不记，要留痕归 journal / insight。别把这条当挡箭牌去挡「你纠正了我」。
- 主动但节流。同一类差一次会话只提一次；用户说「不用记」则该会话不再提这一类；提示只有一句，不解释、不展开、不打断手头的活。
- 主动触发只认明确信号，不做情绪检测。没有信号就不出声；不猜、不劝、不复盘用户的心情。
- 产出场景不打断。用户在写分析、写文档、推方案时那是在产出，不是返工——不在这种时候插澄清。只在「他说的和做的对不上」且确实想改时开口。
- 只清一件事。一次一条 `actual`，不打包；两处不对劲就记两条，第二条等第一条确认完再提。
- 判断都在 agent 侧：把「它就是不行」翻译成具体行为、判断两行是不是同一条差、决定挂在哪件事下，都是 agent 的活，用户只点头或改字。
- 写库三条路：A 级命中明确信号不必先问，直接记，回执一行并附「不想要就说删」；用户点头回应提示；用户已在消息里把「原以为 / 实际做了什么」说清楚，直接记并回执一行。两头都不清时才问一句。过门槛的成本必须低到「你什么都不用做」——问一次就多一次判断成本，嫌烦就永远不记。
- 记歪了用 `--revise <clr_id>` 原地改，重拼提示词、不新增记录；不要手改账本文件（手改最容易漏掉提示词那一份，账本就不自洽了）。删整条才手改文件。
- 规则文本永远是用户的话。工具与 agent 都不代写规则，只把候选顶到用户面前，点头后才落库。
- 数据落点由 CLI 自己选，不用 export。开发版落代码包内 `src/cli/data/`，正式版落 `$XDG_DATA_HOME/qtfounder-lab`（未设则 `~/.local/share/qtfounder-lab`）；只有跑实验、造夹具时才用 `QTFOUNDER_LAB_DATA` 指到临时目录。
- 输出给用户的是提示词原文（`prompt` 字段），不让用户自己组织语言。

## 记录工作流

### A · 过程中命中信号直接入账（一行回执）

命中任一信号就记一条，不必先问：

- 同一个要求用户说了第二遍；
- 用户话里出现「又是这样 / 我又说了一遍 / 不是这个意思 / 别再」；
- 同一处产出被连改三次；
- 用户改掉了 agent 刚定的默认值、常量、路径、命名（「这个应该改成 X」＝我定的那个值被推翻）；
- 用户补了 agent 划的边界（在 agent 说「不做 A」之后加一句「A 也要」）；
- agent 自己发现同类错误在本会话重复（又铺陈、又漏验收）。

动作：自己把「原以为 / 实际」写成两条进 `code clarify --stdin --json`，然后一行回执——`已记 req_xxx / clr_xxx：<一句话的差>，不想要就说删`。不解释、不展开、不打断手头的活。

用户说「删掉 / 不用记」→ 删掉这条（删除无命令，手改账本文件），本会话不再记这一类。记歪了用 `--revise` 原地改。

### B · 收尾主动复盘（每次任务只提一次）

任务交付时跑一次：

```bash
qtfounder-lab code requirement --json
```

当前需求的 `candidates` 里有 `count ≥ 2` 的项，就问一句「这类差第 N 次了，要不要立规则？你给一句话」。等用户给文本，不替它写；同时把 `rules.md` 提醒一句：下次开工前给 AI 看。

### C · 用户召唤

召唤不等于「已有对象」。按顺序：

1. 先定位对象：哪句话、哪个动作、哪次返工。能从上下文认出来，就直接按「澄清的形状」写出三行让用户改。
2. 定位不到就问一句：「要澄清哪一段？」——只问这一句，不上两问。
3. 对象明确但两行还不清，再问：你原本以为它知道 / 会做什么？它实际做了什么？两问必须落到具体行为，答得笼统（「它就是不行」）追问一次「举它刚才那句话或那个动作」。追问后仍笼统，就记用户实际说的那句，不替他编。

### 记一条，拿回提示词

一次把整条记录走 stdin，`--json` 拿结构化结果：

```bash
qtfounder-lab code clarify --stdin --json <<'JSON'
{"before":"我以为它知道我要能直接跑的代码","actual":"给了五段解释加伪代码"}
JSON
```

`prompt` 可省略，省略时按两问拼模板；要新开一件事加 `"task":"<一句话>"`，不加就挂到最近一件事上。把返回的 `prompt` 原文给用户，并说明「可以直接粘回对话」。`deduplicated` 为 true 说明这条之前记过，只提示、不重复记账。

### 用户点头才落规则

```bash
qtfounder-lab code clarify --rule "<用户原话>"
```

落库后回一句：写进了哪个文件、这一批重复差已标为处理过。`rules.md` 由用户自己保管。

## 汇总到档案

账本是逐条记录，档案是提炼后的类型，两者分工不能混。汇总把 `clarify.json` 与 `rules.md` 里攒下的差按主题写进 profile 仓的 `code/intent/`。

账本位置按下面顺序取，取到即止：`QTFOUNDER_LAB_DATA`（临时隔离时才设）；开发版 `<lab 仓>/src/cli/data/`；发布版 `$XDG_DATA_HOME/qtfounder-lab`，未设则 `~/.local/share/qtfounder-lab`。

目标仓是 `data/profile`（`quanttide-profile-of-founder`），分区 `code/`，档在 `code/intent/`。先把 profile 仓 `git pull`，再看 `code/index.md` 里已有哪些主题。

### 分类验收标准

- 主题来自「实际做了什么」这一列，不是来自任务名、日期或工具。同一件事下的多条差，`actual` 归一化后同键的归一类。
- 主题名是协作维度上的短语（如「输出形态与篇幅」「边界与范围」「验收与收尾」），不是命令名、不是产品模块名。
- 已存在的主题档优先归入；确实新类型才新增档，并在 `code/index.md` 的表格里登记一行。
- 一个主题一档，档名用英文 slug（与 `think/`、`work/` 一致）。

### 主题档结构

```markdown
# 主题名

> 来源：澄清账本（`clarify.json`）中 `actual` 归为同一类的记录，涉及 `clr_xxx`、`clr_yyy`；状态：观察 / 类型 / 规则。

**状态：观察。**（出现 1 次）/ **类型**（≥2 次）/ **规则**（已落 `rules.md`）

## 差

一句话说清这一类差是什么：原以为 X，实际 Y。

## 记录

- `clr_xxx`（req_xxx，日期）：原以为 …… / 实际 ……

## 该用的提示词

> 可复用的那句，取自记录里的 `prompt` 或由它归并，仍用第一人称。

## 规则

已落库的规则原话（`rules.md` 那一行）；未立就写「未立」。
```

状态三档照抄 `think/` 的分层习惯：出现 1 次只算观察，≥2 次才算类型，落了规则升为规则。

### 汇总流程

1. 读账本，按 `actual` 归一化键聚成簇，算出每簇次数与涉及记录。
2. 与 `code/intent/` 既有档比对：能归入的归入，不能的才新增。
3. 逐档改写（不是追加）：更新状态、差的一句话、记录明细、提示词、规则节。同一档里同一记录只出现一次。
4. 改了哪些档就同步 `code/index.md` 的表格与 `CHANGELOG.md` 的 `[Unreleased]`。
5. 提交推送：profile 仓 → `data/profile` 子模块指针 → 主仓 → 根仓。

### 汇总边界

- 不改账本：`clarify.json` 与 `rules.md` 只读。要修记录用 `code clarify --revise`，删记录才手改文件。
- 不生成规则：规则文本永远是用户原话；这里只呈现「该用的提示词」和已落库的规则。
- 不搬原文：档案收提炼后的类型与那句提示词，原始每条以 `clr_` id 指回账本；单次出现、不成类型的差留在账本，不进档案。
- 不按日期切档、不按命令切档。

## 示例

```text
（A 级：用户第三次要求同一处改动）
agent：（自己写入库，不问）
       已记 req_1SC3 / clr_X8BG：原以为只改指定段 / 实际整段重写，不想要就说删。
       我原以为「只改我指定的那一段」。
       它实际做了「整段重写」。
       请按我原以为的重做一遍，把这两条当约束。

用户：这一类不用记
agent：（删掉这条，本会话不再记这一类）

（B 级：任务交付时）
agent：（跑 requirement --json，同类差 ×2）
       这类差第 2 次了，要不要立成一条规则？你给一句话。
用户：只改指定段，别动其它
agent：（跑 clarify --rule "只改指定段，别动其它"）已写进 rules.md，下次开工前给它看。

（C 级：召唤但没有对象）
用户：/code-clarify
agent：要澄清哪一段？
```

## 排错

错误一律是 JSON、写在 stderr，退出码三档：

| 码 | 含义 | 常见原因 |
|----|------|---------|
| 0 | 成功（含去重） | — |
| 2 | 用法错 | `--stdin` 少 `before`/`actual`；`--task` 与 `--rule` 同给；`--rule` 文本为空；无可挂的需求（没给 `task` 而库里还没有任何需求） |
| 3 | 未找到 | `--id` 指向的需求不存在 |
